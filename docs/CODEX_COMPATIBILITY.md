# Codex CLI compatibility (contract spike)

## Task 5 adapter slice (isolated only)

`CodexCliAdapter` constructs `codex exec --json --cd <worker worktree> --sandbox workspace-write -c approval_policy=never --model <model> -`, pipes the validated worker prompt on stdin, and uses the shared result-slot quarantine/schema/identity checks. The Codex-specific parser reads `turn.completed` usage and `turn.failed` error events; the process runtime handles timeouts, cancellation, missing/malformed results, and replacement attempts. Arbitrary `extra_args`, additional writable directories and Claude tool grants are refused rather than translated. Fake-Codex unit/integration tests exercise this contract without a model call. This is **not** an enabled worker: `preflightAdapter` and the CLI's Codex runtime gate still deny dispatch because neither the per-command nor allowed-path fence is proved. CLI `workspace-write` is not a complete isolation or result-ownership boundary; the negative security tests below remain decisive. Existing Codex plugin run/resume/delivery skills must remain unavailable.

Verified October 16, 2026 with installed `codex-cli 0.163.0` on Windows, plus the official [CLI reference](https://developers.openai.com/codex/cli/reference/) and [non-interactive guide](https://developers.openai.com/codex/noninteractive/). This is a CLI contract observation, not a claim of Mycelink Codex support.

- `codex exec --json --cd <directory> --sandbox read-only -` accepts a prompt on stdin, emits JSONL to stdout, and exits 0 on a successful authenticated turn. `--model`, `--output-schema <file>`, and `--output-last-message <file>` are exposed by `codex exec --help`; schema-constrained final output and the last-message file were verified live. `workspace-write` is an advertised sandbox mode; avoid `danger-full-access` and `--dangerously-bypass-approvals-and-sandbox`.
- `--ask-for-approval`/`-a` appears on top-level `codex --help` but **not** on `codex exec --help`; `codex exec -a never` exits 2 (`unexpected argument '-a'`). Use the explicit `-c approval_policy=never` override in non-interactive exec; the CLI parses an unquoted TOML value as a literal. Quoted `approval_policy="never"` was accepted in Git Bash but rejected by Mycelink's Windows batch-shim safety policy. Never silently omit approval policy or turn off the sandbox.
- The observed success sequence was `thread.started`, `turn.started`, `item.completed` (`item.type=agent_message`, `item.text`), `turn.completed` (`usage.input_tokens`, `cached_input_tokens`, `cache_write_input_tokens`, `output_tokens`, `reasoning_output_tokens`). The observed isolated unauthenticated invocation produced `error` retries and `turn.failed` carrying an HTTP 401 message; exit 1. Fixture values are sanitized/synthetic.
- On Windows npm installs provide a `codex.cmd` shim and a bash `codex` shim. Native `spawnSync('codex')` did not resolve the executable; use the repository's `planCommand` batch-shim handling for `codex.cmd`. The live test probes this path with `planCommand`.
- Cancellation and tool event payloads, workspace-write enforcement, and plugin hooks are not yet certified by this spike. They require isolated fake and live integration tests before native-host parity can be claimed. An unauthenticated isolated `CODEX_HOME` cannot verify authenticated success; the opt-in test uses whichever profile the tester explicitly elects to run it with.

## Security gate (October 16, 2026)

Codex host-native dispatch is unsupported. The [current official Codex hooks reference](https://developers.openai.com/codex/hooks/) says `PreToolUse` provides `session_id` (shared with a subagent), `turn_id`, `tool_name`, `tool_use_id`, and `tool_input`, but does not promise `agent_id` or `agent_type` for each tool call. Those identity fields are documented for `SubagentStart`; a role label from the model is not an attestation of subsequent tool calls. The Claude fence therefore cannot distinguish controller, worker, and reviewer actions in a Codex `PreToolUse` callback.

The same reference says specialized tool paths can opt out of the default hook path; `write_stdin` does not get another `PreToolUse`, and a hook failure, malformed response, timeout, or unsupported `continue: false` can fail open and Codex continues the tool call. A valid denial is `hookSpecificOutput.permissionDecision: "deny"` (or exit code 2), but successful denials on covered calls do not prove complete per-command enforcement. In particular, `--cd` and `workspace-write` alone do not implement the Mycelink per-allowed-path and result-ownership policy. The in-process fence now refuses `apply_patch` and unclassified MCP calls within detected control workspaces when the hook is actually invoked; this is defense in depth, not an enabled Codex integration.

An isolated local Codex CLI probe using `codex exec --ignore-user-config --json --cd <scratch> --sandbox workspace-write -c approval_policy=never` and a temporary `hooks.PreToolUse` command hook produced `thread.started`, `turn.started`, assistant messages, and `turn.completed` (exit 0). No hook invocation or file write occurred: the installed host rejected the requested `apply_patch` before the hook because the enclosing execution environment enforced a read-only sandbox (`patch rejected: writing is blocked by read-only sandbox; rejected by user approval settings`). An earlier read-only `pwd` probe was likewise rejected by the outer policy. These observations cannot establish whether the configured callback would deny a reachable tool call. No real host-hook parity or bypass resistance was demonstrated.

Until an independent, mandatory, fail-closed boundary can attest role, command, cwd, every writable path, hook registration, and result/reviewer provenance even when Codex bypasses or fails a callback, `codex-cli` preflight fails and the CLI does not activate a Codex worker (including via the fake-Claude override). Tasks 6–15 remain incomplete; Task 5's isolated CLI adapter has only fake-executable coverage and is still gated from production dispatch. The Codex-native host mode must not be advertised or packaged as secure on this evidence.

## Read-only CLI + application-owned MCP broker spike (October 16, 2026)

This is a feasibility observation, **not** a verified security boundary or an enabled worker. The current official [non-interactive guide](https://developers.openai.com/codex/noninteractive/) says `codex exec` defaults to read-only, describes `required = true` for an MCP server (startup failure if it cannot initialize), and includes MCP tool calls in JSONL events. The [sandbox and approvals guide](https://developers.openai.com/codex/sandbox/) describes the OS-level sandbox for model-generated commands, not a sandbox guarantee for a separately launched MCP server. The [configuration reference](https://developers.openai.com/codex/config-reference/) documents `mcp_servers.<id>.required`, `enabled_tools`, and `default_tools_approval_mode` (`auto | prompt | writes | approve`). These are product contracts, not proof that the installed Windows host enforces every built-in tool path.

Isolated probe directory: `C:/Users/psh09/AppData/Local/hermes/cache/scratch/codex-mcp-probe` (not in the repo). The temporary Node stdio MCP server implemented only `initialize`, `tools/list`, and `tools/call` for one tool writing a fixed marker **inside that scratch directory**. Its transport and effects were observed from server-side request records and filesystem existence, not only the model's answer. `codex mcp list` with `-c mcp_servers.mycelink_probe.command=...` and `-c mcp_servers.mycelink_probe.args=...` recognized it without changing a Codex profile. All live runs used installed `codex-cli 0.163.0`, `codex exec --ignore-user-config --ephemeral --json --skip-git-repo-check --cd <scratch> --sandbox read-only -c approval_policy=never -`, with the current authenticated profile for auth only. The scratch artifacts contain raw model responses and are **not** checked into the repository.

### Candidate security architecture (not implemented)

1. **Controller creates an immutable per-claim launch manifest**, binds one Codex process and one trusted broker process to node ID, claim ID, generation, worktree, canonical allowed/forbidden paths, exact gate argv, and a controller-owned output channel. Do not accept role, cwd, claim, or path policy from the model's MCP arguments, prompt, hook fields, or a mutable file in the worker's reach. The controller and reviewer use separate restricted capabilities. Host-native nested Codex agents remain unsupported: a shared session/thread ID is not worker identity.
2. **All model-executable built-in writes must be independently denied** (`read-only` OS confinement, no approval escalation, no writable temp/output/extra dirs, no hidden secondary tool with side effects). The broker is a privileged exception: expose only explicitly classified operations, bind calls to the broker's own launch identity, reject unknown tools and all arbitrary shell/git/system commands. Set `required = true`, explicit tool allowlist, and an approval mode intentionally chosen per tool; do not treat an MCP approval as authorization under Mycelink policy. A process wrapper or child of an unconstrained Codex process is not a boundary merely because the prompt says so.
3. **Writes need an OS-enforced target boundary or race-safe file capabilities**. Lexical/glob checks and `realpath` checks alone cannot stop directory swaps, symlinks/junctions, hardlinks, NTFS alternate streams, or time-of-check/time-of-use races. A per-worker restricted OS account/container mounted with only its worktree's allowed paths, plus a separate broker identity for the result slot, is one option. Another is a broker that accepts bounded *proposals* into controller-owned staging, then applies them using safe handles after validating the full tree and provenance. Neither is verified on this Windows host. Gate execution and git commits also require narrowly scoped, independently enforced operations, not an arbitrary command tool.
4. **Result/review ownership is out-of-band**: broker-sealed result and reviewer verdict channels keyed to separately launched processes and immutable generation IDs, validated after provider exit and checked against on-disk evidence. A JSONL tool-call item, self-reported `node_id`, or a hook callback alone is not proof of who wrote the result. Reconcile after interruption must reject missing/ambiguous provenance.

### Blocking gates before implementation or activation

- In a genuinely isolated test environment, prove the effective `read-only` sandbox denies *every* built-in shell, patch, file-edit, and indirect write (including writable scratch/temp, approvals/escalation, secondary MCP servers and apps), while the required broker remains reachable; verify from filesystem and process observations, not assistant prose. This host's enclosing read-only policy prevents attributing the built-in denial to Codex. Run an attack matrix with absent/crashed broker and failed MCP calls, including turn success despite tool failure.
- Choose and verify a race-safe Windows filesystem/process boundary for per-node allowed paths and the result slot; the current Node path checks and hooks alone are insufficient. Test traversal, symlink/junction and hardlink aliases, alternate streams, directory replacement races, wrong cwd, arbitrary command injection, and role/claim/generation forgery. Prove the worker cannot write a reviewer verdict or controller state and the controller cannot fabricate a worker result.
- Only then implement the broker with failing bypass tests before production code, prove actual live Codex calls and process ownership, run cross-platform regressions, and reconsider the disabled adapter. No hook callback or successful MCP marker is an activation criterion. The workspace-write design in the original plan is superseded by this gate, not silently accepted as secure.

## Native Windows MXC permission-profile counterexample (October 16, 2026)

The installed `codex-cli 0.163.0` has the newer permission profiles described by the official [Permissions guide](https://developers.openai.com/codex/permissions/) and [Windows sandbox guide](https://developers.openai.com/codex/windows/). The former calls profiles beta and describes their scope as *local command execution*: MCP servers, apps, browser, and other surfaces require separate controls. The latter documents MXC as a native Windows process sandbox. `codex -c windows.sandbox=mxc sandbox --permission-profile :workspace -- cmd.exe /d /c echo MXC_OK` succeeded here, while the legacy `elevated` implementation failed (`CreateProcessWithLogonW failed: 267`). This proves that MXC is available for **individual local commands**, not that an entire authenticated `codex exec` process and its tools are isolated.

For a controlled scratch tree under the repository, a custom profile gave `:minimal` read and the workspace root read, with only `allowed/` writable. `codex sandbox -P mycelink_probe -C <scratch> -- cmd.exe /d /c ...` (MXC selected in config) wrote `allowed/control.txt` (exit 0) and denied direct creation of `forbidden/direct.txt` (exit 1). A junction inside `allowed/` pointing to `forbidden/` was also denied (exit 1). **But a hardlink created before launch at `allowed/alias.txt` pointing to `forbidden/result.txt` bypassed the boundary:** writing through the allowed alias exited 0 and changed the forbidden file from `ORIGINAL` to `ATTACK`. A standalone live opt-in test records the negative security assertion:

```text
MYCELINK_LIVE_CODEX_SANDBOX=1 npx vitest run tests/spike/codex-windows-boundary.test.ts --config vitest.config.ts
FAIL: expected 'ATTACK\r\n' to be 'ORIGINAL'
```

The test uses a disposable isolated `CODEX_HOME`, verifies the allowed-write and direct-denial positive controls before checking the hardlink, and removes the scratch tree afterward. The repository's existing Codex preflight remains disabled. This is a demonstrated forbidden-file/result-slot write through an allowed path, not merely a theoretical TOCTOU concern; a path-only preflight that scans aliases before process launch also races with a later hardlink or replacement by another process with access to the tree. It does not establish that the worker itself can create a hardlink under this profile: a separate `mklink /H` attempt inside the sandbox was denied (exit 1). Nor does it establish whether MXC can host an authenticated whole Codex process: attempts to execute `node.exe` and the installed `codex.exe` *inside* `codex sandbox -P :read-only` exited 127 without useful diagnostics on this host, while `cmd.exe /d /c echo` succeeded. Do not attribute those exit codes to a specific Windows or Codex cause without further investigation.

**Decision gate:** Do not treat a Codex permission profile (or a read-only CLI plus a writable MCP server) as the complete worker fence. Before activating Task 5, an independent boundary must prevent hardlink aliases to protected state and races during the whole claim lifetime, attest an actual live Codex process and all side-effecting tools, and bind result and reviewer records to distinct processes/generations. A separate isolated filesystem/identity, or a proposal-only worker whose outputs are applied by a race-safe controller to an isolated tree, is a candidate—not yet implemented or proven on Windows. WSL `bwrap` can start a read-only shell (`bwrap --ro-bind / / --tmpfs /tmp ...` denied a write), but that is Linux evidence, not Windows-native parity and does not by itself close an alias into any writable bind mount. Keep all Codex dispatch disabled until the end-to-end adversarial matrix (hook failure/bypass, unknown tools, alias/race, role forgery, allowed paths, result/reviewer ownership) passes.

## WSL-only boundary follow-up (October 16, 2026)

The user authorized investigation of **WSL-only standalone Codex workers** with native Windows Codex execution still disabled. This does not authorize weakening the security acceptance criteria or imply Codex-native interactive/plugin parity. No runtime adapter or preflight has been enabled.

`tests/spike/codex-wsl-probe.sh` runs in Ubuntu under `psh09`, installing Linux `@openai/codex@0.163.0` only into a disposable WSL `/tmp` tree (removed on exit). A whole Linux Codex CLI process ran inside `bubblewrap 0.11.1` (`--unshare-all --new-session --die-with-parent`, read-only system mounts, private proc/dev/tmp/home, no `/mnt/c` or WSL `/init` bind). `codex --version` returned `codex-cli 0.163.0`; unauthenticated `codex exec --json` emitted `thread.started,turn.started`, then hit a DNS/network failure and was stopped by the 12-second outer timeout (exit 124). The Ubuntu user has **no Linux Codex auth file**, so this is not a completed authenticated worker turn. A hostile shell in that mount namespace could not address a direct protected result or the Windows C: drive, had no `/init`, and had no internet egress. These are shell/process observations, not proof of Codex hooks or MCP behavior.

A writable `--bind <scratch>/worktree/allowed /worktree/allowed` **does not isolate the backing inode**. With a preexisting hardlink from `allowed/alias.txt` to an unmounted protected result in the same WSL tmpfs, the hostile shell changed the protected result from `ORIGINAL` to `ATTACK` even though `/protected` was absent inside the namespace. The opt-in test `MYCELINK_LIVE_WSL_SANDBOX=1 npx vitest run tests/spike/codex-wsl-boundary.test.ts --config vitest.config.ts` is deliberately RED at `protected_result=ATTACK`, not a passing security claim. An alternative scratch-only `--tmpfs /worktree/allowed` overlay prevented this *particular* preexisting alias from changing the result, but its changes disappeared at process exit. It still needs a verified proposal transport, race-safe controller-side application, and separate sealed result/reviewer records. Neither a `realpath` preflight nor this one overlay is a TOCTOU proof.

The network choice is also nontrivial: `--unshare-all` could not resolve Codex's `wss://api.openai.com/v1/responses`, while changing only to `--unshare-all --share-net` plus mounting WSL DNS allowed an unrelated `https://example.com` HTTP 200 request from the supposedly isolated process. An unconstrained shared network would give built-in shell/MCP bypasses arbitrary outbound side effects, even if paths were confined. A scoped API egress bridge/proxy that cannot be repurposed by worker commands, plus a supported WSL authentication contract, is required before live-model end-to-end tests; the [official Codex permissions guide](https://developers.openai.com/codex/permissions/) explicitly scopes permission profiles to local command execution rather than MCP/apps/browsers. In addition, the Windows host can address WSL files outside a sandbox; threat modeling must treat the launcher/controller and its credential bridge as trusted, while the worker process and any subprocess/MCP remain untrusted.

**Still unproved / mandatory before activation:** authenticated Codex turn inside the complete restricted namespace with scoped API egress; arbitrary built-in and MCP side-effect denial when hooks fail or are bypassed; an immutable source snapshot and independently writable proposal path with no shared-inode/TOCTOU escape; node/claim/generation/cwd/allowed-path binding, separate reviewer role and result ownership, interruption/kill/reconcile, and Windows↔WSL process/channel crossing. The existing disabled preflight remains the safe default. Do not create Tasks 5–15 or describe this spike as a shipped worker until the acceptance gate passes.

## Native Windows boundary decision record (October 17, 2026)

Rechecked installed `codex-cli 0.163.0` on `feat/codex-support` without enabling dispatch. The installed CLI advertises `-s read-only|workspace-write|danger-full-access` for **model-generated shell commands**, `--add-dir` for additional writable roots, and an explicit sandbox-bypass option; the [official permissions documentation](https://developers.openai.com/codex/permissions/) limits profiles to local sandboxed commands and assigns MCP, browser, connectors, web search, and Codex service traffic their own controls. The [official Windows sandbox documentation](https://developers.openai.com/codex/windows/) calls its MXC smoke test a *one-command* compatibility check and documents fallback implementations. This is not a whole-process, all-side-effects worker fence.

Reproduce the decisive negative test from the repository root on this Windows host:

```bash
codex --version
MYCELINK_LIVE_CODEX_SANDBOX=1 npx vitest run tests/spike/codex-windows-boundary.test.ts --config vitest.config.ts
```

The October 17 rerun returned `codex-cli 0.163.0`, Vitest exit **1**, and `expected 'ATTACK\r\n' to be 'ORIGINAL'` at line 53. The test creates only disposable scratch files: an allowed path hardlinked *before launch* to a forbidden result. MXC allowed the control write, denied a direct forbidden write, but writing the alias altered the forbidden inode. The source and exact `CODEX_HOME`/permission profile/argv are in `tests/spike/codex-windows-boundary.test.ts`. The test cleans the scratch tree; it does **not** prove an untrusted worker can create that hardlink in-band, nor does it measure a live Codex worker process. A preflight path scan cannot certify a mutable backing tree against a later host-side alias swap; to close the race, the worker must not share writable inodes with protected state throughout the claim lifetime.

Hooks cannot supply the missing boundary. The [official hook reference](https://developers.openai.com/codex/hooks/) explicitly says specialized paths may opt out, `write_stdin` does not get a second `PreToolUse`, a failed/malformed/timed-out `PreToolUse` callback may allow the tool, and `continue: false` on that event is unsupported and continues the tool call. Its `PreToolUse` fields do not attest a per-call `agent_id`/`agent_type`; those fields appear on `SubagentStart`, whereas subagents share the parent `session_id`. A prompt, policy profile, or successful covered-hook denial is therefore not an independently enforceable claim/role/result boundary. The earlier read-only MCP experiment above reached `tools/call` and wrote a scratch marker despite Codex's `--sandbox read-only`; it tested one configured MCP path, not all possible ones. No live hook-failure write was reproducible under the enclosing read-only test harness, so the documented fail-open behavior is a product contract, **not** an additional observed exploit here. Also, the currently served hooks reference now lists `PostCompact` (unlike the earlier plan and October 16 snapshot): this is documentation drift, not evidence that the installed 0.163.0 CLI emits the event. Recheck it in the installed runtime before changing any missing-hook core invariant or claiming host parity.

## Installed Linux hook failure probe (experimental WSL; production DENY)

An authenticated `codex-cli 0.163.0` model-initiated MCP `tools/call` in the isolated WSL launcher ran a configured `PreToolUse` callback when passed explicit inline `hooks.PreToolUse` configuration and `--dangerously-bypass-hook-trust`. The trust override is used **only in this controlled test**, with a fixture callback and the independent bwrap boundary still enforced. The test was RED without hook configuration (MCP call reached, callback marker absent), then GREEN with configuration. Separately, a callback exiting 17, printing malformed output, or exceeding its one-second timeout still led to actual `tools/call` and `turn.completed`. All four runs denied writes through the snapshot hardlink and Windows host path; the protected inode remained `ORIGINAL`. This proves fail-open behavior for the measured MCP path in this installed binary, not `apply_patch` or every built-in path.

Reproduce with `MYCELINK_LIVE_WSL_WORKER=1 MYCELINK_LIVE_WSL_CODEX_AUTH=1` under Ubuntu root and `tests/spike/wsl-worker-isolation.test.py -k test_model_driven_mcp_call_cannot_write_protected_inode_or_windows_host`; set `MYCELINK_HOOK_FAILURE_MODE` to `nonzero`, `malformed`, or `timeout` for the adverse runs. The registered transaction in `scripts/wsl-codex-turn.py` still uses `--ignore-user-config` and supplies no hook configuration, so these standalone probes **do not** establish automatic callbacks in that process. A worker-writable callback marker is observational, not broker-authenticated policy evidence. Hooks must never be the sole authorization for filesystem, network, proposal or settlement access; both production Codex paths remain disabled pending independent end-to-end acceptance.

**Exact missing native-host contract:** an independently imposed identity/process and filesystem boundary for the *entire* Codex worker plus descendants and MCP/hooks/apps, in which (1) only immutable input/snapshot and a private proposal area are reachable, with no shared writable inode or Windows/WSL alias to protected state; (2) outbound and local IPC are capability-scoped, not just shell-profile policy; (3) a trusted controller alone validates/applies proposals to canonical allowed paths and owns gate execution; (4) worker result and reviewer verdict travel in separately authenticated, generation-bound channels that the controller/model cannot forge; and (5) launch, interruption, cleanup, and reconciliation fail closed through claim races. No such native Windows host contract was established here. Do not turn on native Windows `codex-cli` preflight (`src/sessions/preflight.ts` continues to return `ok: false`); the separately authorized WSL-only work can proceed without importing native-Windows parity claims.

Verification of the ordinary provider-config/adapter slice: `npx vitest run tests/unit/provider-config.test.ts tests/unit/adapters.test.ts --config vitest.config.ts` passed 14/14 on this rerun. These tests confirm the existing config/adapter behavior, **not** the proposed native boundary. No full suite or live authenticated Windows worker was run.
