# Codex graph planning (no dispatch)

Find the packaged launcher from **this skill's absolute SKILL.md path**: plugin root is above `skills/mycelink-plan`; verify `<plugin-root>/bin/mycelink.mjs` and `<plugin-root>/dist/mycelink.mjs`. Invoke `node "<plugin-root>/bin/mycelink.mjs"` with quoted absolute paths, never a PATH/cwd/Claude launcher. Stop if either file is missing. Ensure `mycelink.config.json` says `provider.provider: codex` and the approved PRD source exists. The acceptance sidecar is generated by `codex prepare` only after the graph is reviewed.

Write `features/<id>/PLAN.md` and a **draft** graph, copying each approved PRD acceptance criterion's full text, id and kind exactly; do not paraphrase. The CLI can list adapters with `graph adapters --json`; generic `graph import` needs a controller key, so author a reviewed draft without it. Require operator review of repositories, dependencies, allowed/forbidden paths, verification commands and criteria before prepare. Keep hidden evaluator artifacts out of the draft. Leave the fresh control without a key until `codex continue` starts.

After review: `node "<launcher>" codex prepare <id> --source features/<id>/PRD.md --from "<reviewed-draft.yaml>" --kind AC-n=compatibility --control-root "<control>" --json`. This fresh-control-only operation creates the manifest and canonical graph under one validated planning gate; omit `--kind` if every criterion is new behavior. Then `graph validate <id> --control-root "<control>" --json` and inspect `codex status`. Generic `graph compile` requires a controller key and is not the fresh workflow. Do not run `controller open` or `feature init`: `codex continue` opens and holds authority, initialises state once and invokes bounded workers/review. A valid graph is not an implemented or delivered feature.

Before workers run or `codex continue` starts, initialize the fresh disposable control as a Git repository with `git init "<absolute-control>"`. Stage approved inputs explicitly using `git -C "<absolute-control>" add -- <approved-input-paths>` and commit the approved inputs using `git -C "<absolute-control>" commit -m "Record approved planning inputs"`. Replace the path placeholders with the reviewed configuration, repository registry, PRD, PLAN, draft, generated acceptance manifest and canonical graph after prepare and validation; inspect the staged diff before committing. Candidate construction requires a committed control HEAD as well as registered worker Git repositories. Exclude runtime authority, secrets and unrelated files; never copy authority into this control.

For Windows-to-WSL execution, inspect every acceptance shell script before workers run: ensure LF line endings rather than CRLF, including scripts created or checked out on Windows. Normalize affected scripts to LF and run `bash -n "<acceptance-script.sh>"` inside the same WSL environment for each script before `codex continue`. Resolve syntax failures and commit the reviewed script changes in their owning disposable Git repository before workers run. Keep the experimental disposable opt-in explicit and never opt in a production checkout. Standalone `codex resume` and `codex deliver` remain denied; do not bypass with direct generic `dispatch`, `session`, `orchestrate`, `candidate`, `deliver` or `codex exec`.
